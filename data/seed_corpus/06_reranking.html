Reranking em Sistemas RAG

O que é reranking?

Reranking é uma etapa opcional após o retrieval inicial que usa um modelo mais sofisticado (cross-encoder) para reordenar os candidatos recuperados. O retrieval inicial (dense + BM25) é rápido mas aproximado; o reranker é mais lento mas muito mais preciso.

Bi-encoder vs Cross-encoder

O pipeline típico de retrieval usa bi-encoders na fase de indexação: query e documento são codificados separadamente e a similaridade é calculada por produto interno. Isso permite indexar milhões de documentos e fazer buscas em milissegundos.

Um cross-encoder recebe a query e o documento juntos e calcula uma pontuação de relevância diretamente. É muito mais preciso porque pode modelar interações entre os termos da query e do documento, mas é 100x mais lento — inviável para buscar em milhões de documentos.

A solução padrão: usar bi-encoder para recuperar os top-100, depois cross-encoder para reordenar apenas esses 100 e selecionar os top-5 para o contexto do LLM.

Rerankers via API

Nesta plataforma, usamos reranker via API para evitar depender de GPU local:

  • Cohere Rerank: boa qualidade multilíngue, API simples.
  • Voyage Rerank: alta qualidade em inglês e português.
  • Jina Rerank: opção mais barata para volumes altos.

Impacto no Recall@5

Em benchmarks internos, o reranker tipicamente melhora o Recall@5 em 5 a 15 pontos percentuais. O ganho é maior quando o retrieval inicial tem muitos falsos positivos (chunks semanticamente similares mas factualmente irrelevantes).

Quando o reranker piora o resultado?

Se o chunk correto não estiver nos top-100 do retrieval inicial, o reranker não pode salvá-lo. Por isso, o Recall@100 do retrieval deve ser alto antes de adicionar o reranker. Se o Recall@5 cair com o reranker, investigar se o retrieval inicial está devolvendo os chunks corretos nas primeiras 100 posições.
