## 3. Tecnologias (requirements.txt + docker-compose.yml)

- **Vetorial**: Qdrant (qdrant-client, container rag_qdrant)
- **Metadados/BM25**: PostgreSQL 16 (psycopg2-binary) — tsvector como "BM25"
- **Object storage**: MinIO (S3-compatible)
- **Grafo**: Neo4j 5 Community
- **Cache**: Redis 7 (biblioteca redis não está listada em requirements.txt)
- **Embeddings/Reranker**: BGE-M3 e BGE-reranker-v2-m3 locais via FlagEmbedding + torch
- **LLM de geração/visão**: Anthropic Claude (claude-3-5-haiku / claude-3-5-sonnet) — SDK anthropic também não está em requirements.txt
- **Parsers**: PyMuPDF, python-docx, openpyxl, pytesseract+Pillow, opencv+scenedetect, faster-whisper
- **Config**: pydantic-settings + .env

## 4. Achados por módulo (bugs, segurança, más práticas)

### 4.1 requirements.txt — dependências incompletas
Os pacotes `redis`, `anthropic`, `PyYAML`, `numpy` e `neo4j` não constam em requirements.txt, apesar de serem importados diretamente no código-fonte. Isso quebra `pip install -r requirements.txt` seguido de uso normal do pipeline — só é percebido em runtime (a maioria dos imports está em `try/except ImportError`, mascarando o problema como "modo degradado" silencioso).

### 4.2 .env.example desatualizado / documentação inconsistente
`.env.example` referencia `EMBEDDING_PROVIDER=voyage` e `EMBEDDING_API_KEY`, mas `src/config.py` já não usa provider externo (embedding é local, BGE-M3). Também faltam no exemplo: `REDIS_URL`, `NEO4J_URI/USER/PASSWORD`, `TESSERACT_CMD`, `FUSION_TUNED_WEIGHTS`, `ENABLE_CACHE`, `CACHE_*_TTL`, `QDRANT_EF_SEARCH`. Um novo desenvolvedor seguindo o `.env.example` não conseguiria configurar o sistema corretamente.

### 4.3 src/config.py — senhas de dev hardcoded como default (linhas 32, 37, 44)
```python
postgres_url: str = "postgresql://rag:rag_dev_password@localhost:5432/rag_platform"
minio_secret_key: str = "minioadmin_dev"
neo4j_password: str = "rag_neo4j_password"
```
Aceitável para ambiente local, mas são os mesmos valores hardcoded em `docker-compose.yml` — se este projeto for usado como base para produção, essas credenciais fracas tendem a "vazar" para produção por inércia.

### 4.4 🔴 CRÍTICO: src/optimization/caching.py — falha de segurança: cache não isola por ACL/principals
```python
def get_response(self, query: str, tenant_id: str = "") -> Optional[Dict[str, Any]]:
    ...
    cache_key = self._hash_key("rag:resp", f"{tenant_id}:{query}")
```
A chave de cache é derivada apenas de `tenant_id` + texto da query — **não inclui `principals`/ACL do usuário**. Dois usuários do **mesmo tenant** com ACLs diferentes que façam a mesma pergunta **recebem a mesma resposta cacheada**, potencialmente contendo informação de documentos aos quais um dos dois não tem acesso.

### 4.5 🔴 CRÍTICO: src/generation/answer.py e src/generation/self_rag.py — ACL (`principals`) nunca chega à camada de geração
- `answer()` (linha ~324) e `_answer_impl()` (linha ~379) só recebem `tenant_id`, nunca `principals`.
- `adaptive_answer()` em `self_rag.py` (linha ~131) também só recebe `tenant_id`, e chama `routed_hybrid_search()` que **nem tem parâmetro `principals` na assinatura**.

Embora `src/retrieval/hybrid.py::hybrid_search` e `src/retrieval/acl_filter.py::secure_search` suportem corretamente `principals` como pré-filtro, **nenhum caminho de geração de resposta do produto (`answer`, `self_rag`, `query_router`) realmente propaga esse filtro**. O fluxo "principal" documentado no README (`answer()`) não é seguro para ambientes multi-tenant com controle de acesso granular.

### 4.6 src/generation/answer.py::answer_stream — streaming falso
```python
def answer_stream(query, top_k=..., tenant_id=None, model=DEFAULT_MODEL):
    res = answer(query=query, top_k=top_k, tenant_id=tenant_id, model=model, stream=False)
    words = res.answer.split(" ")
    for i, w in enumerate(words):
        yield w + (" " if i < len(words) - 1 else "")
```
A função **espera a resposta completa** (`stream=False`) e só depois faz replay palavra-a-palavra — não há ganho real de time-to-first-token. O streaming de verdade já existe em `_call_claude(..., stream=True)`, mas não é usado aqui.

### 4.7 src/generation/answer.py::_answer_impl — cache de resposta ignora `chunks_used` e citações
No cache hit, o retorno é:
```python
return AnswerResult(
    answer=cached.get("answer", ""),
    chunks_used=[],   # <-- sempre vazio
    ...
)
```
Código downstream que dependa de `chunks_used` (exibir fontes na UI, auditoria) vai falhar silenciosamente quando a resposta veio do cache.

### 4.8 Tratamento de erros fraco/genérico (`except Exception: pass`) — recorrente
Padrão repetido em vários módulos críticos, mascarando falhas reais:
- `src/optimization/caching.py`: `_init_redis`, `get_response`/`set_response` — todos os erros do Redis são silenciados sem log
- `src/generation/answer.py:388-390` e `454-461`: chamadas ao cache envolvidas em `except Exception: pass`
- `src/retrieval/query_router.py:247-251`: `except Exception: graph_hits = []` — qualquer erro de conexão com Neo4j é silenciado
- `src/generation/self_rag.py:167-169, 187-189`: reranking com `except Exception: reranked = candidates[:top_k]` sem log

### 4.9 src/retrieval/bm25_index.py — conexão singleton sem pool/reconexão robusta
```python
_conn = None
def _get_conn():
    global _conn
    if _conn is None or _conn.closed:
        _conn = psycopg2.connect(settings.postgres_url)
    return _conn
```
Sem pool de conexões, sem timeout configurado, conexão global compartilhada entre requisições — em servidor concorrente (ex.: FastAPI com múltiplos workers) não é thread-safe.

### 4.10 src/embedding/embed_index.py — mesmo padrão de singleton global (`_client`), sem tratamento de falha de conexão Qdrant
`_get_client()` não trata exceções de conexão — se o Qdrant estiver fora do ar, o erro sobe cru até o usuário final da CLI, sem mensagem amigável.

### 4.11 src/evaluation/benchmark.py — uso de `Tuple` sem import
```python
from typing import Any, Dict, List, Optional
...
def generate_reports(...) -> Tuple[Path, Path]:
```
`Tuple` nunca é importado de `typing`. Não quebra em runtime por causa de `from __future__ import annotations`, mas qualquer ferramenta de type-checking (mypy) vai falhar com `NameError`.

### 4.12 src/evaluation/benchmark.py::execute_pipeline — `except Exception: pass` mascarando erros de canal
Cada canal (dense/bm25/graph) é envolto em `try/except Exception` retornando lista vazia silenciosamente. Um canal falhando silenciosamente (ex.: Neo4j indisponível) infla artificialmente a comparação a favor de outra configuração sem qualquer aviso no relatório final.

### 4.13 Duplicação de lógica de fusão RRF
Existem **duas implementações distintas de RRF ponderado**: `reciprocal_rank_fusion()` em `src/retrieval/hybrid.py` e `weighted_rrf()` em `src/retrieval/query_router.py`. Ambas fazem essencialmente o mesmo cálculo, mas com estruturas de dados e assinatura diferentes — divergência de manutenção.

### 4.14 src/retrieval/bm25_index.py::search_bm25 — fallback recursivo silencioso pode mascarar erro real de SQL
```python
except psycopg2.Error as e:
    conn.rollback()
    if not use_plain:
        return search_bm25(..., use_plain=True)
    raise e
```
Qualquer erro de sintaxe do Postgres (não relacionado a caracteres especiais da query) também aciona o fallback e mascara a causa raiz.

### 4.15 src/retrieval/routing.py — valores/thresholds mágicos sem calibração documentada
`COMPLEXITY_THRESHOLD = 0.6` é consistente, mas a lógica de pesos hardcoded (`+0.45`, `/3 * 0.3`, `/25 * 0.3`) não tem calibração documentada — não há testes de regressão que validem esses pesos contra o golden dataset.

## 5. Cobertura de testes (tests/)

### 5.1 Testes "fantasmas" — não executados pelo pytest
`pytest --collect-only` confirma que os seguintes arquivos **não contêm nenhuma função/classe reconhecida pelo pytest**:
- `tests/test_generation.py` — testa exatamente o módulo mais crítico (`answer()`) e **contribui 0 testes** ao `pytest`
- `tests/test_evaluation.py` — mesma situação para avaliação offline

Rodar `pytest` no CI **não valida o pipeline de geração de resposta nem a avaliação offline** — são apenas scripts manuais que dependem de infraestrutura viva.

### 5.2 Ausência de mocks / testes de unidade puros para os módulos centrais
Não há `conftest.py`, `pytest.ini` ou `pyproject.toml` no projeto — nenhuma configuração de fixtures compartilhadas, nenhum uso de `unittest.mock`/`pytest-mock` encontrado nos módulos críticos. Os testes de integração dependem de Qdrant/Postgres reais via `docker-compose`. Consequência prática:
- Sem esses serviços de pé, a maioria dos testes falha com erro de conexão, não com falha de asserção
- Não há testes unitários isolados para a lógica pura de `reciprocal_rank_fusion()` sem depender de Qdrant/Postgres reais

### 5.3 Gap específico: cache não tem teste de isolamento por ACL
`tests/test_optimization_latency.py` testa hits/misses e TTL do `CacheManager`, mas **não existe nenhum teste que valide que o cache não vaza dados entre usuários com ACLs diferentes no mesmo tenant** — exatamente o bug de segurança apontado em 4.4.

### 5.4 O que está bem coberto
- Parsers (PDF, DOCX, XLSX, imagem, vídeo, áudio, tabelas) têm testes robustos com fixtures de PDFs sintéticos gerados via `reportlab`
- `test_query_router.py`, `test_routing.py`, `test_self_rag.py`, `test_auto_tune_fusion.py`, `test_benchmark_platform.py` cobrem a lógica de decisão via chamadas diretas de função
- `test_observability.py` testa `record_generation_cost` com e sem trace ativo

## 6. rag.py — entrypoint CLI

`rag.py` é extremamente enxuto (27 linhas) e **suporta apenas o comando `benchmark`**. Não há subcomandos para `answer`, `ingest`, `reindex`, `self-rag` etc. — todo o restante do pipeline só é acessível chamando módulos Python diretamente ou via scripts em `scripts/`, não pela CLI unificada.

A manipulação de `sys.argv` para redirecionar ao `argparse` de `benchmark.py` é frágil: depende da ordem exata dos argumentos — qualquer mudança de assinatura em `benchmark.main()` quebra esse "shim" silenciosamente.
